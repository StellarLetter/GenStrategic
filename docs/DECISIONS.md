## 2026-11-19 · 第五批：中立驻军正常防守、调兵作废改静默

### 变更 A：打中立城市不再累加兵力

**用户原话**

> 现在攻占中立城市兵力会叠加
>
> （追问后选定）中立兵力正常防守；敌方照旧结算。

**推导与落地**

原实现把"中立地块"归进 R4.6 的累加分支（`apply_capture` 里 `army += amount`），
于是 50 兵攻打 40 兵的**中立城市**会得到 50 或 90 兵的城市——中立驻军既没参战也没被扣除。
正确语义按 R3.8（中立对所有人敌对、可被动参战）+ R4.3（阵地战互减）：
中立驻军是一支独立势力，攻占后兵力 = `到达兵力 − 驻军`，打不过就还是中立。

| 议题 | 结论 | 依据 |
| --- | --- | --- |
| 中立驻军是否参战 | **参战**，用伪 owner `NEUTRAL_OWNER = -1` 记入参战集合 | R3.8 "对任何玩家敌对" |
| 攻占后兵力 | `到达 − 驻军`（不叠加） | R4.3 "剩余 = 最大 − 次大" |
| 打不下 | 地块仍中立，驻军减为差额 | R4.4 只在剩余 > 0 时换主 |
| 中立空地（兵力 0） | 照旧：无战斗、直接占领 | R4.6 |
| 敌方地块 | **照旧**（互减后胜方剩余兵力占城） | 用户明确"敌方照旧结算" |

**受影响**：`R3.8` / `R4.4` / `R4.6` 措辞、`game/combat.py`（`NEUTRAL_OWNER` + 守军参战）、
`game/tick.py`（中立守住的落地分支）、`game/rules.py`（`apply_capture` 只对自己地块累加）。
`NEUTRAL_OWNER` 永不写进地块，只出现在 `BattleResult.participants` / `winner` 里。

## 2026-11-19 · 第四批：地图生成、中立语义、聊天播报、预调兵

### 变更 A：地图生成

**用户原话**

> 首都完全随机刷新但是不可出现在曼哈顿距离 12（含）内的两个首都。
>
> 地图大小由人数决定且有小幅随机变动，实际 8 人地图在 30-36。
>
> 地图无对称结构。

**推导与落地**

| 议题 | 结论 | 依据 |
| --- | --- | --- |
| 边长公式 | `size = clamp(6 + 3N + rand(0..6), 10, 40)` | "8 人 → 30..36" 是唯一锚点；线性外推 `6+3N` 在 N=8 时正好是 30，加 `0..6` 抖动得到 30..36。已实测 1..8 人 × 各尺寸区间在曼哈顿 ≥13 约束下都能放下 N 座首都。 |
| 首都约束 | 任意两首都曼哈顿距离 `≥ 13`（即不允许 `≤ 12`） | 用户原话 "距离 12（含）内不可"。 |
| 对称 | **彻底取消**，地形与首都位置独立随机 | 用户原话 "地图无对称结构"。原实现按 180° 旋转成对放首都，并带对称自检，全部删除。 |
| 生成失败 | 换种子重试，边长不变 | 用户明确（Q4）。 |
| 首都可落位置 | 任意格子，含边缘与角落 | 原实现按"离边界距离"优先选内部，该偏好删除。 |

**受影响**：`R2.3`–`R2.7`（新增）、`server/generals/game/mapgen.py`、`config.py`、`net/room.py`（房间不再允许客户端指定边长）。

> 早期实现用**切比雪夫**距离作为首都间距，与本次明确要求的**曼哈顿**距离不等价（切比雪夫更严格），已整体替换。

### 变更 B：中立语义

**用户原话**

> 中立的兵和任何人都是敌对的。
>
> 中立无调兵，但可被动参与战斗，无增长。

**结论**：中立地块保有兵力、对任何玩家敌对、被攻打时按阵地战结算，但**不发起调兵、不增长**。
这是对既有实现的明文确认（原实现已如此），升格为规则条文 `R3.8`。

### 变更 C：聊天栏播报范围

**用户原话**

> 界面优化：聊天栏仅播报停止抵抗（... captured ...）、投降（... surrendered ...）、离开（... left ...）。
> 所以可能出现某人先投降，又被攻占而停止抵抗、随后关闭页面触发离开。

**推导与落地**

| 议题 | 结论 |
| --- | --- |
| 保留的系统消息 | 只有 `"<name> surrendered."`、`"<name> captured <name>. <turn>."`、`"<name> left."` |
| 其它系统消息 | 一律不播（加入、开局提示等全部删除） |
| 玩家发言 | 照常显示 |
| 顺序 | 三条可以先后都播：投降 → 过渡期内被攻占 → 关页面离开 |
| 回合号后缀 | 用户明确（Q5）：`captured` 带回合号 |
| 无攻占者的出局 | 例如投降期满转中立导致失去全部地块，没有攻占方 → **不播** `captured` |

**受影响**：`R6.10`（新增）、`net/room.py` 系统消息生成、`net/chat_log`。

### 变更 D：预调兵

**用户原话**

> 允许从已有调兵链的目标发起调兵请求（称为预调兵，合法性在每 Tick 结算时计算，
> 若 pop 的在结算时出发地不再控制或是调兵数为零，则不再 pop 新请求，
> 但是会无效后续依赖本次调兵的预调兵。
> 修改规则：兵力数小于等于 0 的请求不处理（在结算阶段，发起时不可知调兵兵力）。

**推导与落地**

| 议题 | 结论 | 依据 |
| --- | --- | --- |
| 起点合法性 | 入队**不校验**起点归属；可以是"当前控制的地块"或"链中任意请求的目标" | 用户原话"合法性在每 Tick 结算时计算" |
| 判定时机 | 发起调兵阶段（R7.1 第 2 步） | 用户明确（Q9） |
| 作废条件 | 起点已不归自己 → `src_lost`；算出的调兵量 `≤ 0` → `zero_army` | 用户原话"出发地不再控制或是调兵数为零" |
| 作废后果 | ① 本条不产生移动；② 本 Tick 不再为该玩家弹下一条；③ 下游依赖项一并立即作废 | 用户原话"不再 pop 新请求"+"无效后续依赖的预调兵"；"立刻作废"由用户明确（Q7） |
| 客户端反馈 | 下发 `chain_dropped` 事件 + 重发 `commands` 全量快照 | 用户明确（Q6、Q7） |
| 链形状 | 任意有向图（链、树、**环**） | 用户明确（Q8） |
| 调兵量 `≤ 0` | 请求直接作废（覆盖原先"允许 0 兵力请求"的旧裁决） | 用户原话；推论：1 兵地块调不动 |

**受影响**：`R4.2`（修订）、`R4.11`/`R4.12`（新增）、`R7.2`（补作废）、
`game/commands.py`、`game/tick.py`、`net/*`、`docs/PROTOCOL.md` §2.4/§3.7/§5、`web/src/**`。

## 2026-11-18 · 第一批：规则原文

用户给出的初始规则（唯一事实源），要点：

1. 一秒为一个 **Turn**，分 `Turn N` 与 `Turn N.`；开局 `Turn 0`。
2. 地图是正方形**地块**二维矩形；地块类型：首都、平原、山地、超市。
3. 每地块有兵力值，属于控制者；玩家初始控制首都、1 兵力；其它地块无控制者；城市初始中立 40–50 兵力。
   非中立控制时：首都/城市每回合 +1，平原每 25 回合 +1。视野 = 自己控制区 + 8 相邻 + 视野外城市身份。
4. 每 Tick 可让己方兵力向相邻地块移动 `<出发兵力-1>`；目标存在或同时抵达非友方兵力 → 阵地战；
   战斗后兵力 > 0 → 攻占。相邻两敌对势力同时向另一地块调兵 → 先遭遇战。不可向山地调兵。
5. 每玩家仅一座王城；攻占他人王城 → 占领全部领土，每块继承 `max(floor(原兵力/2), 1)`；
   攻占回合结束时无任何地块 → 停止抵抗，首都转普通城市。
6. 点击选中；WASD 调兵并选中；可缓存多个请求（调兵链），后端按 FIFO 每 Tick 末结算；
   `Q` 取消整链，`E` 取消最新一条；可选点击调兵；面板可看其它玩家兵力与控制区大小。
7. 结算顺序：兵力增长 → 发起调兵 → 遭遇战 → 阵地战 → 更新占领 → 检查停止抵抗；
   对称一致（无随机、不同玩家结算效果相同）。
